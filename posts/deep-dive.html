什么是真正的深挖草稿

2026-10-11 # 思考 # 深挖 # 目的

昨天和师兄聊，他指出我对"挖深技术"可能有误解。这一篇先把这个点记下来，还没展开。

01起因：导师给了一个"新东西"

导师给我发了一个叫 Claude Code Chrome 的东西——一个操控谷歌浏览器的插件。对我来说这其实并不新，因为再往前，ChatGPT 也能够操控浏览器，它有专门的浏览器工具。所以这个能力对我来说感觉并不是很深、很强。

但导师觉得这个很新。因为是导师给我的东西，我就想深挖这一个点。

02我以为的深挖：看源码

但所谓的深挖，其实也只是说我可能会去看看源码之类的。师兄说，这种并不算是深挖。

03师兄说的深挖：针对目的，不断解决目的

// 深挖的定义

深挖是针对于你的目的，然后你会不断地去解决你的目的——这种才叫深挖。

也就是说，深挖不是对一个东西追着看源码、搞懂它怎么实现的。深挖是目的驱动的：你有一个要解决的问题，然后围绕这个问题持续地去解决，在这个过程中自然地深入。

这和之前写的 fake work 其实是呼应的——没有目的的"看源码"，也是一种 fake work。看起来很努力，实际上没有推进任何问题。

04具体例子：智能填表系统

拿我的毕业设计来说。目的是帮助用户用个人或企业的私有数据进行表单填写——这是一个复杂任务，涉及大量表单和多格式问题。

我把它抽象成两个核心动作：找到对应的材料和填写。但直接用 agent 来做，幻觉率特别高。于是做了流程上的拆分：

// 任务拆分 + 门控

找材料 → 判定材料是否合理 → 回答 → 判定回答是否合理
增加两个门控机制，控制流程按预期推进。这没有根本解决幻觉，但相对减轻了。

同时，填表本质上是一个字段抽取问题，所以对模型做了微调，提高它在这类任务上的回答能力。大问题拆成几个小问题，分别去解决、分别去提升。

这整个过程——从目的到任务拆分、到门控设计、到模型微调——每一步都是被目的推着走的，这已经是深挖的起点了。但"拆成小问题分别提升到比较好"还不是深挖的终点。

05深挖怎么继续：边界是跑出来的，不是想出来的

真正的深挖发生在系统跑起来之后。你会不断遇到真实的失败案例，然后一个一个解决。设计阶段能想到的边界是有限的，真正的边界来自真实数据和真实使用。

但可以有一个分类框架，帮你系统性地去找边界：

  • 输入侧（材料）：材料缺失、材料冲突（多份答案不一致）、格式异常（扫描件/图片/表格）、材料超长、相关信息散落多处
  • 过程侧（门控+模型）：门控误杀（该过的没过）、门控漏过（不该过的过了）、模型幻觉、字段需要推理而非直接抽取
  • 输出侧（填写）：格式不匹配（日期/枚举/长度）、字段间依赖、答案需要跨材料整合
  • 系统侧：批量效率、微调数据从哪来、用户反馈怎么回流、隐私部署
// 深挖的具体动作

让系统在真实数据上跑 → 记录每一次失败 → 对失败分类 → 挑最高频的那一类深入解决 → 目的推进一步 → 再跑、再发现新失败。

比如跑着发现"材料冲突"最高频，就自然会去查 RAG 里的证据聚合与冲突消解——这才是被目的驱动的看资料，而不是漫无目的地看源码。

06认识是由浅入深的：先想清楚做什么，再边做边认识

这里涉及一个认识上的问题：认识是由浅入深的，每一个阶段的认识其实都是不一样的。所以不能等"完全想清楚"再做——你在做之前的认识一定是浅的，只有边做边认识，才是最合理的方式。

但话又说回来，还是要想清楚做什么再去做。这里有一个区分：

// 做什么 vs 怎么做

做什么（目的/方向）：需要先想清楚，这是深挖的起点。
怎么做（具体实现/边界）：是在做的过程中逐步清晰的，边做边认识。

这和深挖的定义完全一致：先有目的（想清楚做什么），然后不断解决目的（边做边认识）。不是"先想清楚一切再动手"，也不是"完全不想就做"——而是想清楚方向，然后在做的过程中让认识自然深化。
